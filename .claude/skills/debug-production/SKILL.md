# 本番の不具合を切り分ける

## 0. 先に確認すること

- **利用者影響の有無**。サイト全体が落ちているなら復旧を最優先し、原因究明は後回しにする
- **直前に何を変えたか**。デプロイ・`.env` 編集・VM 再起動のどれかが直前にあるか
- **本番構成を変更する操作は確認を取る**（`CLAUDE.md` の絶対的な制約）

## 1. 切り分けの順序 ★実績でこの順に当たる

**アプリのコードを疑うのは最後。** 過去に踏んだ8件のうち、実装のバグは1件だけだった。

| # | 層 | 疑うこと | 確認 |
|---|---|---|---|
| 1 | **配布** | 未 push / pull 漏れで VM のコードが古い | `git log origin/main..HEAD`（手元）、`git log -1`（VM） |
| 2 | **インフラ** | コンテナが落ちている、nginx の設定・上流 IP | `ps -a`、nginx のログ |
| 3 | **ライブラリの既定値** | 明示していない設定が既定値で効いている | ライブラリのソースを読む |
| 4 | **アプリ** | 自分のコードのバグ | ここまで来て初めて疑う |

**「ローカルでは動く」は何の保証にもならない。** 特に
**ローカルは localhost、本番は実ドメイン**という差が、過去2件の直接原因になっている
（DCR の匿名登録拒否、FastMCP の Host 検査）。ライブラリを入れるときは
「localhost を特別扱いしていないか」を先に確認する。

## 2. ログの読み方（実際に効いた型）

### 「あるべきログが無い」ことを手がかりにする

出ているログだけでなく、**正常なら並ぶはずの列が欠けていないか**を見る。

PWA のリンク横取りを特定したときは、`GET /accounts/login/` が一度も出ず、
代わりに `POST /api/login/` が出ていたことが決め手だった。
サーバは正しく 302 を返しているのにブラウザが従っていない
= **HTTP の外側（OS・ブラウザ）に登場人物がいる**と判断できた。

### 同じバイト数のレスポンスは同一ファイルを疑う

```
GET /.well-known/oauth-protected-resource       200 1008
GET /.well-known/oauth-protected-resource/mcp   200 1008
GET /.well-known/oauth-authorization-server     200 1008
```

内容の違う JSON が偶然同じサイズになることはまずない。
SPA の `index.html` が返っている = nginx の location が効いていない、と特定できた。

### 見慣れないステータスコードは幸運

登場人物が限られるので、発生源を機械的に探せる。

```bash
grep -rln "421" backend/venv/Lib/site-packages/mcp/ .../starlette/ .../uvicorn/
```

421 はこれで数秒で `transport_security.py` に辿り着いた。
400 や 500 だと候補が多すぎて同じ手は使えない。

### 落ちたコンテナは `ps` では見えない

```bash
docker compose -f docker-compose.production.yml ps -a    # ★ -a を付ける
```

## 3. 症状別の当たり所

| 症状 | まず見る |
|---|---|
| `ERR_CONNECTION_REFUSED` | TLS ではなく**誰も待ち受けていない**。nginx が起動できているか（`ps -a` + nginx ログ）。**設定を1つでも読めないと nginx は起動を拒否する**ので、ブロック1つの不備で全体が落ちる |
| 502 Bad Gateway | backend / mcp を作り直した後に nginx を restart したか（upstream の IP はキャッシュされる） |
| `POST` だけ 405 | そのパスが nginx の location にマッチせず SPA に落ちている |
| `POST /mcp` が 421 | FastMCP の許可ホスト（DNS rebinding 対策） |
| `POST /o/register/` が 401 | DCR のパーミッション設定 |
| AS メタデータが 400 | `.env` の `ALLOWED_HOSTS` に認可用サブドメインが無い。**新しい変数を足しただけでは足りない** |
| `openid-configuration` や `/register` を探し始める | **詰まっているサイン**。Claude が推測で探索している。原因は1つ上の応答にある |
| `DisallowedHost` が定期的に出る | ヘルスチェックが Host ヘッダを送っていない |
| `.env` を変えたのに反映されない | 環境変数はコンテナ作成時に確定する。`restart` ではなく `up -d --force-recreate` |
| フロントが古い挙動 | `VITE_` 変数はビルド時に埋め込まれる。再ビルドしたか |
| nginx 設定を変えたのに反映されない | 生成はコンテナ作成時のみ。`up -d --force-recreate nginx` を使う |

事例の詳細は `docs/troubleshooting.md` 項目14〜20、
切り分けの経緯は `docs/mcp-deployment-log.md`（どちらも Git 管理外）。

## 4. 復旧を優先する

原因究明より先に、利用者が使える状態に戻す。

- **一度に1つだけ変える。** 復旧作業中に別の改善を混ぜない（原因が分からなくなる）
- 壊れている機能を**一時的に外して**全体を戻せないか考える
  （認可用ブロックを外して本体サイトを復旧させた例がある）
- nginx が落ちていてポート80が空いているなら、certbot の `--standalone` が使える
- **破壊的な操作の前にバックアップを取る**（DB は `pg_dump`、設定は `cp`）

## 5. 終わったら記録する

同じ問題を二度踏まないために、**切り分けの過程**を残す。結論だけでは価値が薄い。

- 再発しうるなら `docs/troubleshooting.md` に**症状から引ける形**で追記する
- 設計上の判断につながったなら `docs-public/decisions.md` に ADR を足す
- 予防できる構造上の問題なら、それ自体を課題として記録する

書き分けは `write-docs` Skill を読む。**実ドメイン・VM 名・秘密値は書かない。**
